# Content OS — PHASE 1: инфраструктура нового VPS

По §48 ТЗ: этот документ существует **до** того, как что-либо ставится на
сервер. Ничего не разворачивается в рамках Phase 1 — ни строчки на VPS,
ни `docker compose up`. **Обновлено 2026-09-29** — допущение №1 закрыто:
гибрид, локально self-hosted **GigaChat-20B-A3B-instruct-v1.5** (GGUF,
через уже существующий `OpenAiCompatProvider`), облако — Claude как
fallback и для задач, где качество local не проверено (см. `architecture.md`
§2). Конфигурация ниже пересчитана под это, не под «внешний API only».

## 1. Зачем отдельный VPS (напоминание, не решение — уже решено в присланном ТЗ)

Существующий VPS с речевой аналитикой (`speech-service`) не используется —
принципиальное требование заказчика. Content OS получает собственный,
изолированный сервер. Никаких общих Docker-сетей/контейнеров между ними.

## 2. Компоненты на новом VPS

```
Docker Compose
├── reverse-proxy      (Caddy — автоматический HTTPS/Let's Encrypt, проще nginx для одного сервера)
├── n8n                (оркестратор workflow, §31 ТЗ — не все 20 сразу, см. architecture.md §6)
├── redis              (очередь для воркеров на этом VPS — НЕ для Vercel/Next.js)
├── content-worker     (Python или Node — краулинг источников, батч-классификация)
├── llm-inference      (llama.cpp/Ollama — GigaChat-20B-A3B-instruct-v1.5, GGUF, OpenAI-совместимый /v1)
├── telegram-monitor   (Telethon, см. audit.md §14a — если решат переиспользовать заготовку)
└── publishing-worker  (публикация в каналы, где появятся токены — см. integrations.md)
```

`postgres` в composе **не поднимаем** — используем существующую Timeweb
Postgres (architecture.md, database.md). Это отличается от найденной в
Downloads заготовки (audit.md §14a), которая проектировалась со своей
локальной БД — сознательное расхождение, продиктованное текущим ТЗ (§16:
переиспользовать существующую БД).

## 3. Конфигурация — под GigaChat-20B-A3B + n8n/Redis/воркеры

**CPU-only, GPU не нужен** — MoE-архитектура (3.3 млрд активных из 20 млрд)
даёт приемлемую скорость и на CPU, поэтому не переплачиваем за GPU-инстанс.
Расчёт памяти (обсуждали отдельно): модель в GGUF Q4_K_M ≈ **12 ГБ** только
веса, + 1–3 ГБ контекст/KV-cache, + рантайм инференса, + n8n/Redis/воркеры
поверх — итого нужен реальный запас, не «впритык».

| | Минимум (рискованно) | Рекомендую | С запасом |
|---|---|---|---|
| CPU | 4 vCPU | 8 vCPU | 8+ vCPU |
| RAM | 16 ГБ | **24–32 ГБ** | 32+ ГБ |
| Disk | 60 ГБ NVMe | 80 ГБ NVMe | 120 ГБ NVMe (место под несколько квантов модели одновременно, для A/B) |
| GPU | нет | нет | нет |
| Квант модели | Q3_K_M (заметная просадка качества) | Q4_K_M | Q5_K_M (лучше качество, есть запас) |

**16 ГБ — не рекомендую**, несмотря на то, что формально влезает Q4-квант
модели (см. обсуждение выше): это без запаса под n8n/Redis/воркеров,
работающих параллельно — риск OOM при одновременной пиковой нагрузке
(краулинг + генерация + n8n триггер разом). Если бюджет — жёсткий потолок
и больше 16 ГБ не вариант: держать модель на **Q3**, урезать конкурентность
воркеров (`concurrency limits`, §71 исходного ТЗ про Local LLM), тестировать
стабильность до продакшена, не после.

Ценник намеренно не называю (§86 исходного ТЗ прямо запрещает без
актуальных данных провайдера) — смотреть в панели выбранного хостера на
момент заказа. Если пришлёте ссылку/полную таблицу тарифов конкретного
хостера — сверю конкретный тариф с этими цифрами сам.

## 4. Сеть и домены

```
content.единаясреда.рф    → reverse-proxy → n8n (webhook-эндпоинты, за Basic Auth n8n)
content-api.единаясреда.рф → reverse-proxy → content-worker / publishing-worker (Bearer-токен)
```

DNS — A-запись на новом поддомене, TLS — Let's Encrypt через Caddy
(автоматически, без ручной генерации сертификатов).

**Толкование «закрыт от публичного доступа» (§13 ТЗ, допущение №8 в
architecture.md):** Redis — не публикуется наружу вообще (только
`127.0.0.1`/внутренняя docker-сеть, как уже сделано с Postgres в найденной
заготовке — `ports: 127.0.0.1:5432:5432`, тот же принцип). n8n и
content-worker — публикуются, но **обязательно** за аутентификацией
(n8n Basic Auth уже включён в заготовке `N8N_BASIC_AUTH_ACTIVE=true`;
content-worker — Bearer-токен, как `SELFHOSTED_STT_TOKEN`/
`KP_PDF_SERVICE_TOKEN` у уже работающих сервисов). Публичный ≠ открытый
всем — публичный означает «Vercel физически может дозвониться», доступ
контролируется токеном на уровне приложения, а не сетевой изоляцией,
потому что сетевой изоляции между Vercel и любым внешним VPS не бывает.

## 5. Безопасность VPS (§37 ТЗ)

- SSH только по ключу, пароль отключён.
- Не root для запуска сервисов (non-root docker user).
- `ufw`/firewall: разрешены только 22 (SSH, желательно с IP-ограничением
  если у владельца статический IP), 80/443 (reverse-proxy). Все внутренние
  порты (Redis, worker-API) — только на docker-сети/`127.0.0.1`.
- `fail2ban` на SSH.
- `unattended-upgrades` (автообновления безопасности OS).
- Секреты — только в `.env` на сервере (не в git, не в Docker image) —
  тот же принцип, что уже используется для `speech-service`/`pdf-service`
  (`env_file`, `HF_TOKEN`/`API_TOKEN` не в Dockerfile).

## 6. Бэкапы (§38 ТЗ)

- Данные Content OS живут в Timeweb Postgres — бэкапится там же, где весь
  остальной сайт (уточнить у владельца текущую политику бэкапов Timeweb БД,
  не изобретать отдельную).
- На самом VPS постоянных данных, требующих бэкапа, немного (n8n workflow
  definitions, Redis — только очередь, переживаемая потеря): бэкап volume
  `n8n_data` (workflow-конфигурация) — достаточно, Redis не бэкапить
  (эфемерная очередь, worker пересоздаст задачи из Postgres-источника
  правды при потере).

## 7. Мониторинг (§39 ТЗ)

MVP: `GET /health` на каждом сервисе (n8n встроенный, content-worker/
publishing-worker — простой health-эндпоинт как уже сделано у
`pdf-service`/`speech-service`), Uptime Kuma (self-hosted, лёгкий, можно
на этом же VPS) для внешнего пинга + Sentry на Next.js-стороне (если ещё
не подключён — проверить в Phase 4, не переустанавливать вслепую).
Полноценный `Local LLM Observability` (§70 второго ТЗ — модель/latency/
tokens/cost) закрывается таблицей `content_ai_runs` (database.md §7) +
дашборд в самой админке, не внешним APM.
