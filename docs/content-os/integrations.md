## 2. Источники (Topic Hunter) — своя лента Content OS

**Пересмотрено 2026-10-03:** изначально планировалось расширять
«Новостной радар» — владелец явно указал этого не делать: Content OS
должен быть самодостаточным, радар — отдельная, не связанная функция
админки. Теперь свои таблицы (`content_sources`/`content_source_items`,
см. `database.md` §2) и свой парсер (`src/lib/server/contentOsFetch.ts`,
`contentOsSourcePoll.ts`) — логика разбора RSS/Google News/Telegram такая
же по сути, что и в `radarFetch.ts`, но независимая копия, не импорт.
Типы источников те же:
- `keyword` (Google News RSS-поиск по фразе);
- `rss` (прямая RSS-лента);
- `telegram` (открытый веб-просмотр `t.me/s/<канал>`, без токена);
- `website` — физически тянется как `rss`, если по URL есть лента (своего
  парсера произвольных сайтов нет).

Опрос — вручную, кнопка «Собрать сейчас» в Sources (`POST
/api/content-os/sources/poll`) — как и у радара, нет выделенного
cron-слота на Vercel Hobby (см. audit.md §14). Собранные записи попадают в
ленту прямо в Sources, оттуда — кнопкой «→ Создать тему» в `content_topics`
(не нужно переключаться в другой раздел админки).

**Открытый вопрос для настоящего масштабирования Telegram-мониторинга**
(допущение №10 в architecture.md): веб-просмотр `t.me/s/` отдаёт только
~20 последних постов на странице каждого канала при каждом опросе — при
опросе раз в час этого достаточно для большинства каналов (посты выходят
реже, чем раз в 3 минуты), но не годится для «наверстать» после простоя
дольше нескольких часов, и не работает для приватных/закрытых каналов.
Найденный в Downloads `telegram_monitor.py` (Telethon, настоящий API-логин
`api_id`/`api_hash`) снимает оба ограничения. Решение о переносе на
Telethon — на новом VPS (не на Vercel — Telethon держит постоянную сессию,
это process, не serverless-вызов), как отдельный контейнер
`telegram-monitor` (см. infrastructure.md §2). Требует от владельца
`TELEGRAM_API_ID`/`TELEGRAM_API_HASH` (my.telegram.org) и логин обычного
Telegram-аккаунта для сессии.

**Веб-поиск для Research Engine (§22, §77 ТЗ)** — в проекте сейчас нет
интеграции с поисковым API. Варианты (решить в Phase 4, не блокирует
Phase 1):
- встроенный web-search инструмент Anthropic API (если доступен на
  используемом тарифе — самый простой путь, не плодит нового провайдера);
- отдельный провайдер (Brave Search API, есть бесплатный тир; или Google
  Custom Search JSON API).
Пока не выбрано — `ResearchEngine` пишется с интерфейсом `SearchProvider`
и **мок-реализацией**, которая явно возвращает «поиск не настроен» вместо
тихого молчания.

## 3. Публикация

**Обновлено 2026-10-03** — Telegram и VK больше не «интерфейс + мок»:
реальные адаптеры написаны (`src/lib/publishing/`, оркестрация —
`src/lib/server/contentOsPublish.ts`, вызывается из
`POST /api/content-os/items/:id/publish`, кнопка в `ClusterDetail.tsx`).
Код готов, но **ни разу не вызван с настоящими токенами** — без реальных
кредов от владельца протестировать на живом VK/Telegram нельзя.

| Канал | Что есть сейчас | Что нужно для реальной публикации | Статус адаптера |
|---|---|---|---|
| Сайт (ARTICLE) | Полноценный `blogStore`/`dataDb.ts` — публикация статьи уже работает (это существующий блог сайта) | Ничего — переиспользуем как есть | Готов, не мок |
| Telegram | Адаптер готов (`src/lib/publishing/providers/telegram.ts`, Bot API `sendMessage`/`sendPhoto`, без `parse_mode` — тело письма обычный текст, см. комментарий в файле) | Bot API token (@BotFather) + chat_id/`@channel` (бот должен быть админом канала) — вводится в UI вкладки «Каналы», не в `.env` (нужно на компанию, см. database.md §10) | **Готов, ждёт токена** |
| VK | Адаптер готов (`src/lib/publishing/providers/vk.ts`, `wall.post` + загрузка фото через `photos.getWallUploadServer`→`saveWallPhoto`) | Токен сообщества со scope `wall`,`photos`,`offline` (новый, не переиспользовать read-only `VK_STATS_TOKEN`) + id сообщества — в UI вкладки «Каналы» | **Готов, ждёт токена** |
| MAX | Ничего | **Обновление 2026-10-03:** официальный Bot API **появился** (`platform-api2.max.ru`, `POST /messages` умеет постить в канал/группу, не только отвечать). Публикация ботов — только для верифицированных юрлиц РФ (верификация через `@MasterBot`, с августа 2025). ЕдинаяСреда — юрлицо, путь открыт технически, но нужна верификация + токен от владельца | Адаптер **не написан** — приоритет ниже VK/Telegram, но больше не блокер «нет API» |
| Дзен | Ничего (только ссылка в футере) | Официального API публикации постов **по-прежнему нет**. Но есть два легальных обхода, не требующих адаптера вообще: (1) официальный RSS-импорт — завести канал, 10 подписчиков, подтвердить домен, Дзен сам подтягивает статьи с сайта по RSS; (2) бот `@zen_sync_bot` — официальный мост Telegram→Дзен, зеркалит текст+видео из Telegram-канала автоматически | Не нужен отдельный адаптер — Дзен закрывается через (1) или (2), не через `src/lib/publishing` |
| Email | — | `[ОТЛОЖЕНО]` | — |

```ts
// src/lib/publishing/interfaces.ts — уже реализовано
export interface PublishingProvider {
  readonly channel: "vk" | "telegram";
  publish(input: PublishInput, credentials: Record<string, string>): Promise<PublishOutput>;
}
```

**Известный компромисс:** токены хранятся в `content_channel_profiles.credentials`
(jsonb) в открытом виде — защита только через `requireAdminAccess`, без
шифрования на уровне поля. Это соответствует текущему уровню риска проекта
(нигде больше нет field-level encryption секретов в БД), но стоит иметь в
виду при аудите безопасности (`security.md`) — если понадобится, следующий
шаг — симметричное шифрование (AES) с ключом в `.env`, не меняющее схему.

**MVP-путь без токенов не сломан:** пока `credentials` пустые, кнопка
«Опубликовать» в UI вернёт понятную ошибку («не настроены groupId/accessToken»),
и остаётся ручная отметка «Отметить вручную» — контент готовится и
утверждается независимо от того, подключены токены или нет (audit.md,
риск №5).

## 4. Email `[ОТЛОЖЕНО]`

Транзакционная инфраструктура уже есть (`src/lib/server/mailer.ts`,
SMTP через домен Timeweb) — **не годится напрямую** для кампаний без
дополнительного слоя (список получателей, отписка, репутация домена, см.
audit.md риск №6). Когда вернёмся к email — здесь появится `EmailProvider`
интерфейс (§9 ТЗ) и решение по конкретному провайдеру после разговора с
владельцем (не выбираю сейчас).
