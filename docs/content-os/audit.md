# Content OS — PHASE 0: аудит существующей системы

Только аудит. Кода нет. Следующая фаза (архитектура) не начинается без
подтверждения владельца — см. «REQUIRED INPUT FROM OWNER» в конце.

## 1. Версия Next.js

**15.4.8**, App Router, React 19.1.2, TypeScript 5, ESLint 9. `package.json:64,69-70`.

## 2. ORM

**Нет ORM.** Прямой SQL через `pg` (`node-postgres`) — пул соединений в
[`src/lib/timewebPg.ts`](../../src/lib/timewebPg.ts), паттерн everywhere:
`create table if not exists` в коде (лениво, при первом обращении), без
отдельной миграционной системы/CLI. Файлы миграций в `supabase/migrations/*.sql`
существуют, но это **справочные SQL-снимки для ручного прогона**, не
управляемые миграции (нет версионирования/rollback-механизма).

## 3. База данных

**Timeweb Cloud PostgreSQL** — основная и единственная активная БД
приложения. Строка подключения `DATABASE_URL`/`TIMEWEB_DATABASE_URL`,
TLS с бандл-CA (`certs/timeweb-cloud-ca.pem`), пул `max=3` на инстанс
(рассчитан на Vercel serverless — много holodных стартов, лимит соединений
у управляемой БД). `DATABASE_SEARCH_PATH` — по умолчанию `public`, но часть
таблиц (AI Sales) исторически жила в схеме `es_app` (см. `timeweb_es_app_schema.sql`,
`timeweb_ai_sales_cleanup_esapp.sql` — судя по названию, часть данных уже
мигрировали обратно в `public`; актуальную схему по каждой таблице проверять
явно, не полагаться на комментарии в коде).

**Побочная находка:** в `package.json` есть `@supabase/supabase-js`, и в коде
есть `src/lib/supabase.ts`/`supabaseServer.ts` — но использует их **только**
`src/app/test-supabase/page.tsx` и `src/app/test-comments/page.tsx` (тестовые
страницы). Весь реальный контент (`posts`, `news`, `comments` — см.
`src/lib/server/dataDb.ts`) идёт через `/api/data/*` → Timeweb Postgres, не
Supabase. Похоже на артефакт прошлой миграции с Supabase на Timeweb.
**Supabase для Content OS не рассматривать как активную БД** — разве что
владелец скажет, что она всё ещё где-то нужна.

## 4. Можно ли использовать текущую БД для Content OS

Да, технически — таким же способом, каким уже живут `radar_*`, `letters_*`,
`kp_*`, `ai_*` (AI Sales), и таблицы `cf_*` контент-завода, которые я уже
создал в этой же сессии (см. §16, есть открытый вопрос по их судьбе).
Главный практический риск — **не место**, а **соединения**: пул на инстанс
рассчитан под serverless (`max=3`), а Content OS по ТЗ подразумевает ещё и
постоянные воркеры на отдельном VPS, которые тоже будут держать соединения к
той же БД параллельно с Vercel-функциями. Нужно будет либо отдельный
connection-pooler (в заметке про КП уже упоминается pgBouncer на порту 6432
как решение для похожей проблемы под нагрузкой — см. `kp-features-and-setup`
в памяти), либо явный лимит на воркеров. Уточнить у Timeweb фактический лимит
одновременных соединений на тарифе.

## 5. Есть ли PostgreSQL

Да (см. §3). Версия сервера не проверена из репозитория — нужно посмотреть
в панели Timeweb (обычно 15/16, но не гадаю).

## 6. Можно ли добавить pgvector

**Не проверено — требует ответа от Timeweb/владельца** (управляемая БД,
права на `CREATE EXTENSION` не гарантированы на всех тарифах). Важная
находка: **у проекта уже есть работающий RAG без pgvector** — база знаний
AI Sales (`supabase/migrations/timeweb_ai_knowledge_base.sql`,
`src/lib/server/aiSales/kbDb.ts`): документы режутся на чанки, эмбеддинг
(Yandex, 256 измерений) хранится как `jsonb`-массив, косинусное сходство
считается **в коде приложения**, не в БД. Комментарий в коде прямо говорит:
«масштаб БЗ небольшой, pgvector не нужен». Для Brand Knowledge Base
Content OS это готовый, проверенный в продакшене паттерн — можно
переиспользовать без ожидания ответа по pgvector, и включать pgvector
только если/когда объём базы знаний реально упрётся в производительность
JS-перебора (это стоит явно измерить, а не предполагать заранее).

## 7. Какие существующие API можно переиспользовать

- **LLM-провайдер уже абстрагирован** — `src/lib/ai/interfaces.ts`
  (`AiProvider.generateStructured()`) + реализации `AnthropicProvider`
  (Claude, `@anthropic-ai/sdk`, structured output через `zodOutputFormat`),
  `YandexGptProvider`, `OpenAiCompatProvider`. Это ровно то, что ТЗ Content OS
  просит в §34 (`LLMProvider`) — не создавать новую абстракцию, расширить эту
  (добавить `embed()`/`classify()` при необходимости — `generateStructured` уже
  покрывает `generateText`/`generateStructured`/`classify` через Zod-схему).
- **Email (транзакционный, не кампании)** — `src/lib/server/mailer.ts`
  (nodemailer, домен-почта Timeweb, SMTP), `src/lib/server/bounceScan.ts`
  (imapflow — сканирование отказов). Используется для отправки одного письма
  клиенту (КП, письма). **Не production email-платформа**: нет управления
  списком получателей/отписками/кампейн-трекингом open/click за пределами
  того, что уже сделано вручную для КП (`letter_sends` — открытие письма по
  pixel/ссылке). Фундамент есть, campaign-слой (§4-10 ТЗ) — новый.
- **VK** — только чтение статистики группы (`src/lib/server/social.ts`,
  токен сообщества со scope `stats`) и OAuth-вход пользователей сайта
  (`src/lib/oauth.ts`). **Публикации (wall.post) нет** — нужен отдельный
  токен сообщества со scope `wall`, `manage`.
- **Telegram** — только что добавлено **чтение** публичных каналов
  (`src/lib/server/radarFetch.ts`, парсинг `t.me/s/<channel>`, без токена)
  для мониторинга. **Публикации (Bot API sendMessage) нет.**
- **MAX, Дзен** — интеграций нет вообще, только статичные ссылки в футере
  сайта. Дзен и MAX публичных/официальных API для автопубликации на момент
  этого аудита я подтвердить не смог (см. переписку про MAX-каналы ранее в
  этом чате) — по §50 ТЗ («не придумывать API») для обоих нужен либо адаптер
  с официальной документацией (если найдётся), либо явная заглушка/мок до
  появления доступа.
- **Bitrix24** — `src/lib/server/bitrix/*`, REST через входящий вебхук + explicit
  event webhook. CRM-интеграция, не издательский канал, но может быть точкой
  для будущих лид-уведомлений.
- **Мониторинг источников / Topic Hunter — уже частично существует.**
  Новостной радар (`src/lib/server/radarDb.ts`, `radarFetch.ts`,
  `src/lib/radarTypes.ts`): триггеры (`keyword` через Google News, `rss`,
  только что добавленный `telegram`), сбор в `radar_items`, категоризация,
  статусы. Это прямое пересечение с §19 ТЗ (`source` → `source item` →
  `topic extraction` → `classification` → `duplicate detection`). Не готовый
  Topic Hunter (нет дедупликации, нет кластеризации, нет scoring по несколько
  критериям), но избавляет от нуля.

## 8. Как устроена авторизация

Собственная, без внешних auth-провайдеров (кроме OAuth-входа для сайта):
- `src/lib/server/userSession.ts` — подписанная cookie-сессия пользователя
  (`AUTH_SESSION_SECRET`), проверка в `authFromBearer.ts::getUserFromRequest`.
- `src/lib/server/editorSession.ts` — отдельная cookie-сессия «редактора»
  (`EDITOR_EMAIL`/`EDITOR_PASSWORD`/`EDITOR_SESSION_SECRET`) — обходной вход
  в контент-функции без записи пользователя в БД (используется для admin-API:
  `requireAdminAccess` = editor-cookie ИЛИ `role==='admin'` в БД).
  passwords — bcryptjs.
- RBAC — **одна колонка** `user_profiles.role` (свободная строка), базовые
  значения `admin | author | user` для контента (`assertCanWriteArticles`,
  `assertAdmin` в `authFromBearer.ts`), плюс отдельный расширенный набор
  `admin | rop | manager | analyst` **для того же поля**, но интерпретируемый
  только внутри модуля AI Sales (`SalesRole` в `authFromBearer.ts:92`).
  Модель расширения: не новая таблица ролей, а новые допустимые значения +
  своя проверочная функция на модуль. Content OS может пойти тем же путём.
- OAuth (Яндекс, VK) — только для входа обычных пользователей сайта
  (`src/lib/oauth.ts`, `src/app/api/oauth/*`), не связано с правами админки.

## 9. Как устроен deployment

**Vercel**, судя по `vercel.json` (`crons`), `.vercelignore`,
`next.config.ts` — обычный serverless-деплой из этого же git-репозитория
(`origin` → GitHub, деплой триггерится пушем в `main`, отдельного
`.github/workflows` нет — значит именно встроенная GitHub-интеграция Vercel,
не self-hosted CI). Судя по `docs/ai-sales/architecture.md` — план **Hobby**:
лимит **2 крона** в `vercel.json`, не чаще раза в сутки каждый — оба уже
заняты (`letters/bounces/scan`, `radar/refresh`). Это подтверждено самим
`vercel.json` (ровно 2 записи). Проверить у владельца, не сменился ли план.

## 10. Как работает речевая аналитика

Отдельный self-hosted Python-микросервис **`speech-service/`** (в этом же
репозитории, но не часть Next.js-приложения): FastAPI-подобный `app.py`,
`Dockerfile`, faster-whisper + pyannote.audio для диаризации на моно-записи
(разделение говорящих без стерео-АТС). Судя по README: разворачивается
отдельно (`docker build` + `docker run -p 8000:8000`), должен быть доступен
**из интернета по HTTPS** (через nginx/Caddy reverse-proxy), потому что
Vercel-функции обращаются к нему как к внешнему HTTP-API
(`TRANSCRIPTION_PROVIDER=selfhosted`, `SELFHOSTED_STT_URL`,
`SELFHOSTED_STT_TOKEN` — Bearer-токен). **Не могу подтвердить из репозитория,
развёрнут ли он прямо сейчас и на каком именно сервере** — это и есть тот
«существующий VPS», который упомянул владелец в задаче, но факт и адрес
живого инстанса — только со слов владельца (см. REQUIRED INPUT).

## 11. Какие Docker-контейнеры уже существуют (в репозитории)

Два независимых Docker-сервиса, оба Python, оба по одному паттерну
(reverse-proxy + Bearer-токен, публичный HTTPS-эндпоинт):
1. **`speech-service/`** — распознавание речи (см. §10), порт **8000**.
2. **`pdf-service/`** — конвертация DOCX→PDF через LibreOffice headless
   (`pdf-service/README.md`), порт **8001**. Судя по формулировке в памяти
   проекта («развернуть pdf-service») — **похоже, ещё не развёрнут**
   (KP-генератор явно отдаёт DOCX и «понятную ошибку» на PDF, если
   `KP_PDF_SERVICE_URL` не задан). Не утверждаю однозначно — подтвердить
   у владельца.

Ни `docker-compose.yml`, ни оркестрации между ними в репозитории нет —
каждый разворачивается и живёт независимо (сам README `pdf-service` это
прямо говорит: «может жить на том же сервере — просто отдельный контейнер
и порт», «Не связан со speech-service»).

## 12. Какие порты используются

Из репозитория подтверждается: `speech-service` → **8000**, `pdf-service` →
**8001** (оба — дефолты из README/Dockerfile, реальные порты на проде могут
быть переопределены при разворачивании — не гарантия). Next.js локально —
**3215** (`.claude/launch.json`, только для dev). На Vercel порт не
применим (serverless).

## 13. Какие домены используются

Основной: **единаясреда.рф** (+ `media.единаясреда.рф`, судя по
`next.config.ts` `remotePatterns` — под медиа/аплоады). Второй домен
компании упоминается в собственной документации контент-завода
(`ecorostov.ru`) — не проверено, обслуживается ли он этим же Next.js-проектом
или отдельно; не утверждаю. Доменов/поддоменов под `speech-service`/
`pdf-service` (типа `stt.единаясреда.рф`) в репозитории не встретил —
скорее всего они настраиваются вне кода (DNS/reverse-proxy на самом VPS,
значения только в env на Vercel).

## 14. Какие cron/фоновые задачи существуют

- `vercel.json`: `letters/bounces/scan` (06:00 UTC ежедневно),
  `radar/refresh` (04:00 UTC ежедневно) — это и есть оба «слота» Hobby-плана.
- **Очередь фоновых AI-задач без выделенного cron** — `ai_jobs` в Postgre
  (`FOR UPDATE SKIP LOCKED`, см. `docs/ai-sales/architecture.md`), дренируется
  либо вручную (кнопка «Обработать очередь» в дашборде AI Sales →
  `POST /api/ai-sales/jobs/drain`), либо внешним планировщиком
  (cron-job.org и т.п.) с `Authorization: Bearer $CRON_SECRET` — **потому
  что третьего слота под vercel-cron уже нет**. Это готовый, уже работающий
  паттерн ровно для той проблемы, которую Content OS упрётся снова
  (много этапов пайплайна, Hobby-план не даёт добавить cron на каждый).

## 15. Где лучше разместить Content API

Рекомендация (не решение — на усмотрение владельца при утверждении
архитектуры): **внутри существующего Next.js** как `/api/content-os/*`
(по аналогии с `/api/ai-sales/*`, `/api/kp/*`) для всего, что дергает
браузер админки напрямую (CRUD тем/контента/email) — не плодить отдельный
backend ради этого. Тяжёлые/долгие операции (краулинг источников, рендер
email, публикация) — выполнять на новом VPS (n8n/воркеры), которые дергают
`/api/content-os/*` обратно как webhook-клиент с Bearer-секретом (тот же
паттерн, что уже есть у `CRON_SECRET` и у `speech-service`/`pdf-service`
токенов) — потому что **Vercel serverless не даёт держать долгоживущий
процесс/подключение**, значит оркестрация обязана жить вне Vercel, а не
внутри API route.

## 17. Как лучше подключить новый VPS

Через тот же паттерн, что уже проверен в проде для `speech-service`/
`pdf-service`: **публичный HTTPS-эндпоинт за reverse-proxy (nginx/Caddy) +
Bearer-токен**, не «приватная сеть» — потому что Vercel serverless физически
не имеет доступа к приватной сети/VPN VPS, вызовы идут снаружи через
интернет в обе стороны. Это отличается от буквального прочтения §13 ТЗ
(«все сервисы закрыты от публичного доступа») — толковать как «закрыты
для всех, кроме аутентифицированных запросов по токену», а не «недостижимы
из интернета», иначе Vercel не сможет их вызвать. n8n — то же самое:
публичный webhook-URL + собственная auth n8n (Basic Auth/API key на вебхуках),
не «открыт всем».

## 18. Связь между новым VPS и существующей системой

Два канала, оба уже есть как прецедент:
1. **Vercel → VPS**: HTTP(S) к сервисам на VPS с Bearer-токеном (как
   `SELFHOSTED_STT_TOKEN`, `KP_PDF_SERVICE_TOKEN`).
2. **VPS → Vercel/Timeweb**: воркеры на VPS дергают `/api/content-os/*` с
   `CRON_SECRET`-подобным токеном (как уже делает внешний планировщик для
   `radar/refresh`) **или** подключаются к Timeweb Postgres напрямую по
   `DATABASE_URL` (тот же SSL CA, см. §4 — учитывать лимит соединений).
   Что из двух — решить на этапе архитектуры по каждому воркеру отдельно
   (прямые записи в БД быстрее, но обходят валидацию/бизнес-правила,
   которые сейчас живут в Next.js API routes).

## 19. Доступ к Timeweb DB с нового VPS

Технически — обычная строка подключения (`DATABASE_URL` + CA-сертификат,
код уже это умеет в `timewebPg.ts`). **Не проверено**: разрешает ли текущий
firewall/whitelist Timeweb-БД подключения с произвольного нового IP, или
там ограничение по IP/VPC — узнать в панели Timeweb при заказе VPS
(желательно оба сервера в одном дата-центре/VPC Timeweb, если это возможно,
для меньшей задержки и чтобы не открывать БД всему интернету).

## 20–21. Минимальный и «с запасом» VPS

**Тут прямое противоречие между двумя присланными частями ТЗ**, вижу два
документа, регулирующих архитектуру AI по-разному:
- Документ с §1–53 (полный ТЗ, «ЗАДАЧА: Построить AI Content OS»), §12:
  «AI inference **НЕ запускать локально** на VPS без отдельного решения.
  Использовать **API моделей**».
- Отдельный присланный ранее фрагмент «LOCAL LLM INFRASTRUCTURE» (§53–88)
  прямо противоположно требует **обязательный** локальный inference
  (Ollama/vLLM) на новом VPS.

Я не могу молча выбрать один из двух — это меняет конфигурацию сервера на
порядок (CPU/RAM без GPU vs. GPU-инстанс с 16+ ГБ VRAM). Пока держу два
сценария:

**Сценарий A — только внешний LLM API (n8n + Redis + воркеры + email-рендер, без inference):**
- MVP: 2 vCPU, 4 ГБ RAM, 40 ГБ NVMe, без GPU — этого достаточно для n8n +
  Redis + несколько лёгких Node/Python воркеров при нагрузке ~30–150
  контент-единиц/месяц (не параллельный realtime-трафик, а фоновая очередь).
- С запасом: 4 vCPU, 8 ГБ RAM, 80 ГБ NVMe — если добавится краулинг большего
  числа источников и параллельный рендер email-превью.

**Сценарий B — с локальным inference (Ollama, CPU) поверх сценария A:**
- MVP: 8+ vCPU, 16 ГБ RAM (под модель уровня `medium`/7B quantized) — тот
  же класс, что уже описан в README `speech-service` для CPU-инференса.
- С GPU (vLLM, для скорости): отдельный GPU-инстанс, 8–12+ ГБ VRAM —
  дороже на порядок, отдельный провайдер (не все VPS-хостинги дают GPU).

Стоимость по обоим сценариям не называю — зависит от прайса конкретного
хостера на дату заказа, называть цифры без актуальных данных провайдера
не буду (это и в самом ТЗ отдельно запрещено, §86 первого документа).

## 22. Email provider уже используется?

Нет выделенного campaign-провайдера (Mailchimp/SendGrid/UniSender и т.п.).
Есть только прямой SMTP через доменную почту Timeweb для транзакционных
писем (см. §7). Если Content OS должен слать 30 HTML-рассылок в месяц
именно как **кампании** (массово, с отпиской/трекингом open-rate по всем
клиентам, не одному адресату за раз) — прямой SMTP для этого не
предназначен (риск спам-репутации домена, нет built-in unsubscribe-листа,
нет open/click трекинга кроме того, что уже вручную сделано для
`letter_sends`). Это должно быть в «REQUIRED INPUT» — см. ниже.

## 23. Существующие API Telegram/VK/MAX/Dzen

См. подробно §7. Коротко: VK — только чтение статистики + OAuth-вход;
Telegram — только что добавленное чтение публичных каналов (без токена);
MAX, Dzen — только статичные ссылки в футере, интеграций нет.
**Публикации ни в один из четырёх каналов сейчас не существует.**

## 24. Какие environment variables потребуются

Ориентировочно (не финально — уточнится на этапе архитектуры):
`CONTENT_OS_API_URL`/`CONTENT_OS_WEBHOOK_SECRET` (Vercel↔VPS), `N8N_BASE_URL`+
auth, `REDIS_URL` (только на VPS, не в Vercel env), `EMAIL_PROVIDER_*` (после
выбора провайдера кампаний, см. REQUIRED INPUT), `TELEGRAM_BOT_TOKEN`
(публикация), `VK_COMMUNITY_TOKEN` со scope `wall,manage` (публикация,
отдельно от уже существующего `VK_STATS_TOKEN`), `DZEN_*`/`MAX_*` — по факту
появления официальных API. Если решится локальный inference (см. §20–21) —
`LOCAL_LLM_*` набор уже описан во втором присланном документе (§59) дословно.

## 25. Потенциальные проблемы и риски

1. **Противоречие в ТЗ по локальному inference** (см. §20–21) — блокирует
   выбор конфигурации VPS, пока не решено.
2. **Судьба уже построенного `cf_*` контент-завода** (см. §16) — не удалить
   молча то, что могло уже использоваться.
3. **Лимит соединений Timeweb Postgres** при добавлении постоянных воркеров
   поверх и так serverless-нагруженного пула (см. §4).
4. **Vercel Hobby: 2 крона уже заняты** — вся оркестрация Content OS обязана
   идти через VPS/внешний планировщик, не через `vercel.json` (см. §14).
5. **Нет ни одного реального API публикации** ни в один соцканал — контент-план
   на 140 единиц/месяц упрётся в «нечем публиковать», пока не появятся
   токены Telegram Bot API, VK `wall`-токен, и решится вопрос MAX/Dzen.
   Реалистично Content OS первой версии будет **готовить** контент и
   отдавать на публикацию человеку (copy-paste/ручная публикация), пока
   API-адаптеров нет — стоит явно заложить это в MVP, а не блокироваться.
6. **Email как кампании, а не транзакционные письма — по сути новый
   продукт** (список получателей, отписка, антиспам-репутация домена,
   deliverability) — использование текущего SMTP-домена без отдельного
   провайдера кампаний рискует репутацией самого домена для транзакционной
   почты (КП, письма), если объём/жалобы вырастут.
7. **Не подтверждено, развёрнуты ли `speech-service`/`pdf-service` сейчас и
   где** (см. §10–11) — если «существующий VPS» уже перегружен или его
   характеристики неизвестны, я не могу оценить, насколько буквально
   выполнимо требование «не переносить и не смешивать» без базовых фактов
   о нём.
8. **pgvector не подтверждён** (см. §6) — но есть рабочая альтернатива,
   так что это низкий, не блокирующий риск.

   или мигрировать данные в новую схему?
3. **Email как маркетинговые кампании** — использовать существующий SMTP
   Timeweb-домена как есть, или нужен отдельный campaign-провайдер
   (Mailchimp/UniSender/SendGrid/Postmark и т.п.)? Если провайдер уже
   выбран или есть предпочтение — назвать, чтобы не изобретать API (§50 ТЗ).
4. **Реальный статус `speech-service`/`pdf-service`**: развёрнуты ли они
   сейчас, на каком сервере, какие у этого сервера характеристики (это и
   есть «существующий VPS» из задачи, или другой)?
5. **Бюджет и хостер под новый VPS** — есть ли предпочтение по провайдеру
   (тот же Timeweb, что и БД, ради меньшей задержки и, возможно, единого
   биллинга — или другой)?
6. **Токены каналов публикации**, которых сейчас нет: Telegram Bot API
   token (+ id канала/чата для публикации), VK community-токен со scope
   `wall`/`manage` (отдельно от текущего read-only `VK_STATS_TOKEN`),
   доступ к API Дзен/MAX для публикации, если он вообще существует у этих
   платформ — без них Content OS сможет готовить контент, но не публиковать
   его автоматически (это ок для MVP, но нужно понимать сроки появления
   токенов для планирования фаз).
7. **Права на `DATABASE_URL`/сеть Timeweb для нового VPS** — нужно будет
   либо явно разрешить IP нового VPS в панели Timeweb (если там есть
   whitelist), либо подтвердить, что доступ открыт по паролю/сертификату
   без ограничения по IP.
8. **Согласие на буквальное толкование §13 ТЗ** («сервисы закрыты от
   публичного доступа») как «закрыты для неаутентифицированных запросов»,
   а не «недостижимы из интернета» — иначе Vercel не сможет вызывать
   сервисы на VPS (см. §17).
