# Content OS — план реализации (после аудита Postmill)

Этот документ отвечает на задачу «взять Postmill за основу Content OS».
Короткий ответ, обоснованный в `docs/postmill-integration-audit.md`:
**код/рантайм Postmill не берём** (архитектурно несовместим с «не отдельный
сайт, не вторая система пользователей», плюс AGPL-лицензия). Вместо
переписывания с нуля — продолжаем уже существующий Content OS
(`docs/content-os/`), который был спроектирован той же дисциплиной
«аудит → архитектура → БД → API → UI» в сессии 2026-09-28/29 и уже реально
переиспользует auth/БД/AI-слой/layout админки.

Ниже — пункты A–J из задания, и актуальный статус/следующий шаг для
`Content OS`.

## A. Что забираем из Postmill без изменений

**Ничего.** Код Postmill нельзя скопировать без двух проблем сразу:
(1) он написан под его собственный бэкенд (NestJS) и БД-схему (Prisma),
не под прямой SQL текущего проекта; (2) лицензия AGPL-3.0 требует
раскрытия исходников производной работы при сетевом использовании —
решение, которое не принимается молча на уровне реализации (см. аудит §2).

## B. Что адаптируем (идеи, не код)

- Daily-snapshot аналитика (не live fetch при каждом открытии дашборда) —
  применимо к уже спроектированной `content_analytics`.
- Идемпотентная публикация (один item → один канал → одна активная попытка)
  — это уже заложено в `content_publications` (`database.md` §6), Postmill
  просто подтверждает, что паттерн правильный.
- Каталог прав (ресурсы × действия) — держать в уме как возможное будущее
  расширение текущей модели ролей (`user_profiles.role`), если понадобится
  более гранулярный approval-флоу, чем сейчас.
- UI-идеи календаря (drag-to-reschedule, таймзоны) — как требования к
  доработке `ContentPlanTab.tsx`.

## C. Что добавляем сами (нет ни у Postmill, ни у нас)

- **Brand Brain с AI-экстракцией из брендбука** (§7 исходного промпта):
  загрузка PDF/DOCX/PNG/JPG/SVG → извлечение цветов/шрифтов/логотипа/
  типографики/запрещённых элементов → ручная коррекция владельцем. Ни
  Postmill (у него Brand Kit — ручной ввод, не AI-экстракция), ни текущий
  Content OS (сейчас `content_brand_documents` — просто текстовые
  документы под RAG, без визуального разбора) этого не делают. Это
  отдельная, нетривиальная фича, которую нужно спроектировать отдельным
  проходом (OCR/vision-модель для разбора брендбука), не внутри этого плана.
- **AI Content Strategist** (§10) и **Monthly Content Plan с approval-гейтом**
  (§11) — в текущем Content OS есть темы/кластеры/контент-план, но нет
  отдельного шага «AI предлагает контент-стратегию на основе бизнес-целей
  и прошлой аналитики» как самостоятельной сущности.
- **QA-пайплайн PASS/REWORK/HUMAN REVIEW** как явный статус (§17–18) —
  сейчас QC есть (brand/seo/fact check), но не формализован как
  обязательный гейт со статусами именно в этих трёх значениях.

## D. Что лучше вынести в n8n

Без изменений от предыдущего аудита (`docs/content-os/architecture.md`,
`infrastructure.md`): n8n — оркестратор на новом VPS для долгих/фоновых
процессов, которые не может держать Vercel serverless — краулинг
источников, батч-классификация, публикация с ретраями. n8n нигде сейчас
не запущен; есть неразвёрнутая заготовка (`Downloads/.../автоматизация/`)
с собственной Postgres — её схема не подходит (спроектирована не под
Timeweb), полезны только `telegram_monitor.py` (Telethon) и общая идея
воркфлоу как референс.

## E. Что лучше вынести в отдельный AI-service

Не выносим ничего нового отдельно от уже принятого решения: гибрид
self-hosted (GigaChat-20B-A3B через `OpenAiCompatProvider`, на новом VPS)
+ облачный Claude как fallback — уже решено 2026-09-29
(`docs/content-os/architecture.md` §Допущения, п.1) и уже используется в
AI Sales (см. недавние коммиты про таймауты self-hosted LLM). Единственное
дополнение по этому плану — **Timeweb AI Gateway как ещё один
`OpenAiCompatProvider`-конфиг** (см. аудит §3) для задач, где нужен облачный
шлюз без прямого ключа конкретного вендора.

## F. Какие таблицы БД добавляем

Полный список уже спроектирован в `docs/content-os/database.md` (ещё не
применён к БД — Phase 2 там помечена как ожидающая подтверждения):
`content_clusters`, `content_briefs`, `content_items`, `content_item_versions`,
`content_topics`, `content_topic_dedup`, `content_research_packs`,
`content_research_sources`, `content_seo`, `content_fact_checks`,
`content_brand_documents`, `content_brand_chunks`, `content_brand_feedback`,
`content_channel_profiles`, `content_publications`, `content_analytics`,
`content_prompt_versions`, `content_ai_runs`. Этот план ничего нового сюда
не добавляет, кроме будущих таблиц под Brand Brain (п. C) — те не
проектируются в этом документе, отдельный проход.

## G. Какие таблицы существующей БД переиспользуем

- `radar_triggers`/`radar_items` — расширяются (не заменяются) под Topic
  Hunter (уже сделано частично: AI-классификация тем).
- `user_profiles` — авторизация/роли, без изменений схемы.
- `ai_kb_documents`/`ai_kb_chunks` — не трогаем (домен AI Sales), Content OS
  получает параллельные `content_brand_documents/_chunks` по тому же
  паттерну (RAG без pgvector).
- Старые `cf_*` (первая версия «контент-завода») — уже удалены по решению
  владельца (см. `scripts/drop-content-factory.sql`, коммит `b3474d6c`).

## H. Какие Docker-сервисы нужны

Без изменений от `infrastructure.md`: на новом VPS — `reverse-proxy` (Caddy),
`n8n`, `redis` (только очередь воркеров VPS, не для Vercel), `content-worker`,
`llm-inference` (GigaChat-20B GGUF), `telegram-monitor` (опционально,
Telethon), `publishing-worker`. `postgres` в compose **не поднимается** —
используется существующая Timeweb Postgres. Ничего из Docker-образов
Postmill не используется (п. A).

## I. Сколько ресурсов VPS потребуется

Без изменений от `infrastructure.md` §3 (расчёт под гибрид с локальной
GigaChat-20B-A3B): рекомендованная конфигурация — **8 vCPU, 24–32 ГБ RAM,
80 ГБ NVMe, без GPU** (MoE-архитектура не требует GPU). Минимум (рискованно)
— 4 vCPU/16 ГБ, не рекомендуется из-за риска OOM при одновременной нагрузке
n8n+воркеры+инференс. VPS пока не куплен.

## J. Риски

1. **Юридический риск AGPL** (новый, см. аудит §2) — если кто-то решит
   буквально копировать код Postmill «чтобы сэкономить время», это создаёт
   обязательство раскрыть исходники сервиса. Нужно явное решение владельца,
   если этот путь вообще рассматривается всерьёз.
2. Все риски из предыдущего аудита Content OS остаются в силе и не решены
   этим документом: лимит соединений Timeweb Postgres при добавлении
   воркеров VPS; отсутствие реальных токенов публикации (Telegram Bot API,
   VK `wall`/`manage`, MAX/Дзен — у двух последних официальное API для
   публикации не подтверждено вообще); новый VPS не куплен; реальный статус
   `speech-service`/`pdf-service` не подтверждён из репозитория.
3. **Риск повторного «снесём и переделаем».** Это уже второй раз, когда
   контент-модуль проектируется с нуля (`cf_*` → Content OS → этот аудит).
   Прежде чем менять направление ещё раз, стоит явно решить объём MVP и
   не пересматривать архитектуру по каждому новому внешнему примеру
   (Postmill, другие SaaS), иначе Content OS не доедет до продакшена.

## Следующий шаг

Ничего не переписывается. Решение по Postmill закрыто (аудит выше),
новых миграций/кода в рамках этого ответа не создавалось. Следующий
реальный шаг для Content OS — тот же, что был намечен и раньше, но ещё не
выполнен: применить `database.md` (Phase 2, реальные `create table`),
затем довести уже спроектированный Phase 7+ (дедуп по эмбеддингам,
research-движок) — и отдельно, по желанию владельца, начать проектирование
Brand Brain (п. C) как самостоятельную фичу.
