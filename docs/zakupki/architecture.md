# Единая среда — интеграция с закупками (44-ФЗ / 223-ФЗ)

Проектный документ. Код по этому плану **не написан** — здесь оценка источников
данных, рекомендуемый подход и решения, которые нужно принять до реализации
(в первую очередь — платный сервис или нет).

## Зачем

ЕИС в сфере закупок (zakupki.gov.ru) — не источник контента, а источник
**лидов и рыночных данных**: тендеры на инвентаризацию кладбищ/зелёных
насаждений/лесоустройство по всей стране (44-ФЗ/223-ФЗ), и уже заключённые
контракты конкурентов (цены, регионы, объёмы) для контраргументации в КП и
для контента рубрики «Успехи клиентов»/«Тенденции».

Это две разные по сложности задачи — их стоит разделять с самого начала:

| | Извещения (объявленные закупки) | Реестр контрактов (уже заключённые) |
|---|---|---|
| Что даёт | **Лид**: можно подать заявку | Рыночная аналитика: кто выиграл, за сколько, где |
| Актуальность | Только пока приём заявок открыт (окно 5–30 дней) | Историческая, не срочно |
| Сложность доступа | Высокая — официального API нет, обсуждение ниже | Ниже — есть недорогие сторонние API |

## Источники данных — что есть на самом деле

1. **Официальный сайт (zakupki.gov.ru), поиск через UI**
   Формы `extendedsearch`, поддерживает экспорт найденного в XML по клику
   «Экспортировать в XML». Официального REST/JSON API для программного
   поиска **нет**. Сайт — сессионный, Java-based, возможны антибот-меры.
   Автоматизировать поиск через эмуляцию браузера технически можно, но
   хрупко (вёрстка/защита меняются без предупреждения) и в серую зону по
   духу (хотя данные сами по себе открытые и публикация обязательна по
   44-ФЗ). **Не рекомендую как основной канал** для продакшена.

2. **Официальные открытые данные (opendata)**
   `zakupki.gov.ru/epz/opendata/` — обязательная по 44-ФЗ публикация: полные
   выгрузки в XML по фиксированным XSD-схемам (`fcsNotificationEF44`,
   `fcsContract44` и т.д.), архивы по регионам, обновляются ежедневно.
   Это **весь** объём закупок по стране — гигабайты в день. Бесплатно и
   официально, но:
   - нужен отдельный процесс скачивания + распаковки + парсинга XML —
     **не помещается в Vercel serverless** (лимиты по времени выполнения и
     памяти; даже на Pro это будет тесно для полного нац. объёма);
   - фильтрация по нашим ключевым словам возможна только постфактум, после
     скачивания и разбора — то есть инфраструктура всё равно нужна, просто
     без абонплаты.

3. **Сторонние API-обёртки над теми же официальными данными** — уже
   агрегируют и дают поиск по ключевым словам/региону через простой JSON.
   Нашёл минимум три при беглом поиске: DaMIA (`damia.ru/apizakupki`),
   `ofdata.ru/api/contracts`, `newdb.net/yur/contracts`. По беглому обзору
   это в основном **реестр контрактов** (уже заключённые), не факт что
   покрывают именно активные извещения — нужно проверять у каждого вендора
   отдельно перед оплатой.

4. **Коммерческие тендер-платформы с алертами** (Тендерплан, Контур.Закупки,
   Seldon.Basis, RTS-Tender и т.п.) — построены именно для того, что нужно
   нам: подписка на ключевые слова/регион/закон → уведомление о новом
   извещении **на email** или в личном кабинете. Это готовый продукт для
   лидогенерации по тендерам, а не сырые данные.

## Рекомендуемый подход — поэтапно

### Этап 1 — рыночная аналитика (дёшево, быстро, не срочно)

Взять один из недорогих API реестра контрактов (п.3) и через Vercel Cron
(или ручную кнопку, см. ограничение ниже) раз в сутки тянуть новые контракты
по нашим ключевым словам («инвентаризация кладбищ», «зелёные насаждения»,
«лесоустройство», «паспортизация территории», «ГИС муниципалитет» и т.п.).
Складывать в `zakupki_contracts` (заказчик, победитель, сумма, регион, закон,
дата, ссылка). Небольшой трафик, укладывается в serverless без проблем.

Даёт: сравнение цен по регионам для КП, повод для контента («сколько стоит
инвентаризация кладбища в вашем регионе»), список потенциальных клиентов,
которые уже проводили похожие закупки (значит, ещё вернутся).

### Этап 2 — реальные лиды по активным тендерам

Здесь официального дешёвого пути нет — два реалистичных варианта:

**Вариант A (рекомендую): email-дайджест от тендер-платформы.**
У проекта уже есть рабочая инфраструктура приёма и разбора почты
(`imapflow`/`mailparser`, `src/lib/server/mailAccountsDb.ts` — используется
для обработки бounces писем). Подписываемся на алерты по ключевым словам в
одной из платформ п.4 (у части есть бесплатный/дешёвый тариф на email-алерты
без полного API-доступа), они присылают письма на выделенный ящик, наш
парсер вытаскивает из письма: заголовок закупки, заказчика, НМЦК, регион,
срок подачи, ссылку на извещение — и кладёт в `zakupki_leads`.
Минимум нового кода (парсер письма + маппинг в таблицу), никакого
скрапинга официального сайта, работает в рамках уже одобренной архитектуры.
Стоимость — подписка на выбранную платформу (нужно выбрать и оплатить).

**Вариант B: свой краулер open-data (бесплатно, но тяжелее).**
Скачивать только нужные регионы/срез open-data, фильтровать по ключевым
словам. Не влезает в Vercel — нужен отдельный воркер. Реалистичный
бесплатный вариант: **GitHub Actions по расписанию** (без VPS) — скрипт на
Node скачивает срез, фильтрует, шлёт найденное вебхуком в
`/api/data/zakupki/ingest` на защищённый секретом эндпоинт (как cron с
`CRON_SECRET` уже сделан для радара). Дороже по разработке и по
сопровождению (формат/схемы open-data меняются без предупреждения), но
без ежемесячной платы.

**Решение по варианту A vs B — за вами**, это единственная развилка,
требующая выбора до начала кода (в основном потому что A стоит денег
ежемесячно, а B — стоит времени на разработку и поддержку).

## Ограничение инфраструктуры (важно)

Проект на **Vercel Hobby**, где на весь проект **2 крона в `vercel.json`**
(уже заняты: `letters/bounces/scan` и `radar/refresh`), и не чаще раза в
сутки каждый. Новый cron в `vercel.json` не добавляем — по аналогии с тем,
как уже решено для очереди AI Sales (`docs/ai-sales/architecture.md`):
- кнопка «Проверить закупки» в админке (ручной POST);
- внешний планировщик (cron-job.org и т.п.) → `POST /api/data/zakupki/refresh`
  с `Authorization: Bearer $CRON_SECRET`, как уже сделано для `radar/refresh`.

## Предлагаемая схема БД

```sql
-- Этап 1: рыночная аналитика (реестр контрактов)
create table zakupki_contracts (
  id text primary key,           -- номер реестровой записи
  law text not null,             -- '44-fz' | '223-fz'
  customer_name text not null,
  customer_inn text,
  winner_name text,
  region text,
  subject text not null,         -- предмет контракта
  price numeric,
  signed_at bigint,
  source_url text,
  matched_query text,            -- какой ключевой запрос нашёл эту запись
  created_at bigint not null
);

-- Этап 2: активные лиды (извещения)
create table zakupki_leads (
  id text primary key,
  law text not null,
  customer_name text not null,
  customer_inn text,
  region text,
  subject text not null,
  nmck numeric,                  -- начальная максимальная цена контракта
  submission_deadline bigint,    -- срок подачи заявки — главное для приоритизации
  notice_url text not null,
  status text not null default 'new',  -- new/qualified/submitted/lost/won
  matched_query text,
  source text not null,          -- 'email-digest:<провайдер>' | 'opendata'
  created_at bigint not null,
  updated_at bigint not null
);
```

## Где показывать в админке

Не в «Контент-заводе» — это не контент-маркетинг, а лидогенерация/продажи.
Предлагаю отдельный раздел админки **«Закупки»** (по образцу `NewsRadar`/
`AiSalesSection`): список активных извещений с сортировкой по сроку подачи
и НМЦК, статусы (Новая → Квалифицирована → Подана заявка → Выиграна/
Проиграна), карточка контракта с кнопкой «Создать сделку» (интеграция с
AI Sales/Bitrix, если решим вести как сделку) и отдельно — кнопка «В тему»
для успешных/интересных кейсов, закидывающая их в контент-завод как тему
рубрики «Успехи клиентов»/«Тенденции» (тот же паттерн, что уже есть у
радара → контент-завода).

## Что нужно решить, чтобы начать кодить

1. Вариант A (email-алерты, платно) или B (open-data + GitHub Actions,
   бесплатно, но дольше делать и поддерживать) для Этапа 2.
2. Если A — какую платформу оплачиваем (нужен доступ/тестовый период,
   чтобы посмотреть реальный формат email-дайджеста перед тем, как писать
   парсер под него).
3. Если B — тестовый прогон на open-data одного региона, чтобы оценить
   реальный объём и трудозатраты парсинга перед тем, как автоматизировать
   на всю страну.
4. Этап 1 (реестр контрактов) можно начинать без решений выше — она не
   зависит от выбора по Этапу 2 и один из недорогих API-агрегаторов можно
   взять сразу, если подтвердите бюджет на него.
